# Дорожная карта проекта (черновик v0.2)

Уточнения автора, учтённые при упорядочивании (v0.2):
- Языки: C++ (ядро) + Python (скриптинг/моды), pybind11-биндинги. Графика — существующая (OpenGL/glad).
- «Медленное обновление» в текущем виде (slow_tick/slow_tick_indices) — плохая реализация; замена на on_slow_tick через NBT + глобальный перемешанный массив World. «Чатичного» в исходном списке — опечатка, имеется в виду «частичного».
- Коллизии переведены на собственный лёгкий AABB-движок (Static/Entity/Fragment/Trigger); Bullet и его shape-обёртки удалены.
- Перемещение сущностей — логика «блок A → блок B» с проверкой возможности прохода до выдачи команды, а не просто один физический шаг.
- Ручная расстановка чанков в test.py — вынужденная мера для отладки в ограниченных рамках; целевая генерация World должна быть динамической.
- Меши vs коллизии: геометрически одинаковы; нужно лишь разделить меши на «используемые физикой» и «не используемые физикой».
- Два типа блоков: статические (камень, земля — общие для мира) и уникальные (печи, сундуки — инвентарь/состояние, не влезает в 16 бит данных блока).
- NBT (uint16): 12 бит значений; используется для вариативности мешей (повороты), смешанных текстур (трава по биомам) и пр.
- Медленный тик: массив uint32[524288] = 32×512×32 — принцип «один ко всем»: вмещает все номера блоков чанка (у всех чанков одна геометрия), и каждый такт по 32 значения из него рассылается ВСЕМ загруженным чанкам ⇒ гарантированная псевдослучайная обработка, полный цикл одного блока ≈ 13.65 мин (524288 / (32×20)).
- Разнесённое хранение: до 32768 статичных блоков (плоский массив id) + до 32768 уникальных (вектор внутри ChunkNugget); ссылки на блоки с id >= 32768 ведут на уникальные блоки чанка.
- Items — относительно сложные объекты: предмет в инвентаре + бросаемый/поднимаемый объект в мире; взаимодействие с блоками (установка) — отдельный случай. Сундуки — «наполовину сущности».
- UI — базовый класс поверх экрана (частичное/полное перекрытие, возврат/невозврат мыши, реакция на события); конкретное содержимое (меню, инвентарь, инвентарь блока) значения не имеет.
- Сохранение не зависит от генерации: сохранение = превращение известных данных в формат для диска; если работает с 1 чанком — заработает с любым количеством. Поэтому его можно делать ДО динамической генерации.
- Глобальный файл проекта — ФИНАЛЬНЫЙ шаг (не первый): точка запуска «код сам из себя», список миров World (может быть несколько), подключение модов при запуске. Требует не своей реализации раньше других, а гибкости классов на всём протяжении roadmap (например, возможность заменить алгоритм освещения модулем, вписав логику вызова после создания World). Реализуется последним шагом.

## Принципы упорядочивания
1. **Гибкость — сквозное требование, а не задача.** Каждый класс делается с расчётом на позднюю замену поведения модулями/модами (освещение, генерация, тики). Это условие приёмки для всех пунктов, а не отдельный этап.
2. **Фундамент данных → механики → мир → представление → интеграция → финальная сборка.**
3. **Каждая задача опирается только на уже сделанные.** Никаких циклических зависимостей в порядке.

### Фаза 3. Мир
| № | Задача | Зависит от | Комментарий |
|---|--------|-----------|-------------|
| 9 | Сохранение объектов + механизм динамического сохранения/загрузки чанков | 3, 7 | Не зависит от генерации: сериализация известных данных (включая NBT и уникальные блоки); критерий — работает с 1 чанком ⇒ работает с любым составом. Чанки будут хранится как одельные файлы с их данными. В блоки и сущности, соответственно, нужно будет добавить функции для сохранения, возвращающие нужные данные, а в их менеджеры (для Entity нужно добавить менеджер как класс прямо в его модуль) добавить функции для загрузки, точнее генерации, объектов из этих данных (т.е. определённую фабрику). Это позволит сохранить и загрузить любые объекты.|
| 10 | Создание кода примитивной динамической генерации World и модуля для биомов | 9 | Детерминированный простой генератор вместо ручной расстановки 2×2 в test.py; границы ограничены сознательно (переход к п.11 без поломок). Т.е. просто нужно генерировать чанки, пусть даже без заполнения, или сохранять-загружать их, при выгрузке-загрузке. Например по мере передвижения dummy (в последствии - игрока). Модуль для биомов будет состоять из класса биома и класса для их хранения, при этом последний - должен обладать очень гибкой системой для встраивания биома в текущую карту (разделение пирога), и функцией для их получения по 6 значениям (для этого нужно создать шаблон класса для генерации шума Перлина и добавить в данный модуль структуру с 6 значениями, сам модуль доделаем позже). Это можно сделать по аналогии с TerraBlender от Minecraft, т.к. у него схожая логика. В классе биома должна быть функция (пересоздаваемая в дочерних классах) для получения цвета листвы данного биома, а в чанк нужно добавить 1024 (32x32) массив с id биомов (uint16), что бы можно было быстро обращятся к ним через класса для их хранения, а не высчитывать из по 6 значениям каждый раз.|
| 11 | Создание кода динамической генерации World | 10 | Полный генератор: биомы, рельеф, NBT-вариативность (трава по биомам). Для этого нужно создать генератор шума Перлина, который должен возвращать значение по xz (или xyz) координате. В качестве объекта с параметраим о биоме можно использовать [Temperature (Температура), Humidity (Влажность), Continentalness (Континентальность — близость к океану или центру материка), Erosion (Эрозия — плоская равнина или крутые горы), Weirdness (Странность — пики гор, долины, реки), Depth (Глубина)] (как в TerraBlender). Как воспринимать полученные данные код будет решать самостоятельно. Так, к примеру, блок травы сможет обратится к 4 биомам (смещение в 0.5 блока не критично, но уменьшит затраты с 9 до 4 вызовов), получить значения из функций из классов биомов (например getGrassColor()) и интерполировать из них цвет плоскости в шеёдере.|

## Примечания
- Пункты 5→6 делаются подряд: сначала разбор текущего состояния коллизий, затем разделение мешей на физические/рендерные.
- Пункт 8 частично параллелен с 6 (проверка проходимости требует рабочих коллизий из 5, но не финального вида мешей).
- Порядок 9→10→11: сохранение осмысленно и тестируемо независимо от генерации (по уточнению автора); генерация подключается к уже готовому механизму загрузки/выгрузки.
- Items (п.4) остаются в фазе данных: их «мировая» половина (item-entity) дотестировывается в п.8 и п.12 (подбор через UI), но сами классы описаний/стаков создаются рано — на них завязаны инвентари уникальных блоков.
- Окно Windows-CMake сознательно вне roadmap (rebuild + тестирование дешевле создания).

## Открытые вопросы (для v0.3)
1. Формат mod-хуков: достаточно ли Python-колбэков на событиях жизненного цикла (post-world-create, replace-light-engine и т.п.), или нужна C++--side таблица интерфейсов? Влияет на объём п.14.
2. Item-entity в мире: хранится в том же «уникальном» векторе чанка, что и уникальные блоки (п.3), или в отдельном списке сущностей чанка/мира? Влияет на порядок 4 и 8.
3. Медленный тик (п.7): распространяется ли он на уникальные блоки (печи/сундуки) наравне со статическими, и участвуют ли item-entity в той же рассылке?
